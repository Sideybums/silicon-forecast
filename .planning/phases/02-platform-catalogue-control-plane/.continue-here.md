## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention mechanism |
|---|---|---:|---|
| Disposable DB mistaken for a backend | `npm run test:db` proves migrations in an ephemeral PostgreSQL container; it stores no operational observations. | blocking | Verify an explicit durable connection, migration ledger and row counts before calling SQL operational. |
| Lossy collector-to-SQL mapping | Current enums, nullability, evidence hashes, IDs and qualification terms do not match the SQL contract. | blocking | Add raw/staging tables and an explicit versioned adapter with quarantine and fixture tests. |
| Mystery blank cells | Aggregate abstentions cannot explain which MPN/retailer target failed or why. | blocking | Persist every collection attempt, including non-observations, keyed to run and target identity. |
| Broad but shallow catalogue | 242 MPNs look extensive, but most have only one retailer target. | advisory | Measure exact-MPN retailer depth and freshness before presenting comparison breadth. |
| Browser coupled to operational SQL | A live database/API dependency would add failure modes before the backend is proven. | advisory | Retain a deterministic checksum-bound static export from reviewed SQL views initially. |

## Verified backend reality

### Operational architecture

```text
launchd collector
  → immutable candidate tranche + evidence ledger committed to Git
  → checksum/approval-gated public JSON
  → static Next.js build
  → Cloudflare assets
```

There is no persistent SQL ingestion, runtime query path or database-backed frontend.

### Existing SQL observation capability

`candidate_primary_retail_observation` can represent:

- canonical product/revision and exact expected/observed MPN;
- retailer, source and versioned source policy;
- observed/retrieved timestamps;
- seller identity and relationship;
- item price in minor units, currency and VAT evidence;
- availability;
- delivery and landed-price state;
- qualification state/reasons;
- HTTPS source URL;
- evidence reference/hash;
- append-only observations and retailer-product price movements.

It structurally supports multiple retailers and multiple dated observations per MPN.

### Missing or incompatible persistence

The SQL model/pipeline does not losslessly retain:

- collection run, target window/cursor, collector version and Git commit;
- tranche identity/path/SHA-256;
- each attempted target and each failed attempt;
- HTTP status and final URL;
- response SHA-256, response bytes and retention state as distinct fields;
- evidence-ledger SHA-256 and structured evidence facts;
- parser/extractor version;
- raw seller/availability/delivery/qualification vocabulary.

Current direct-load incompatibilities include collector `availability.normalised = other`, null extract hashes, null delivery destination, colon-bearing observation IDs, different qualification vocabulary and mandatory canonical-product foreign keys for MPNs not present in the four-product SQL seed.

### Coverage

Target registry:

- 242 distinct MPNs;
- 416 exact MPN/retailer targets;
- six retailer families;
- retailer depth distribution: 141 MPNs with one retailer, 55 with two, 24 with three, 17 with four, five with five, none with six or more.

Current public MPN evidence depth:

- `CMK32GX5M2B6000C36`: 2 retailer identities;
- `KF560C30BBEK2-32`: 4 retailer identities after normalising duplicate CCL display names;
- `KF564C32RSK2-32`: 4 retailer identities after normalising duplicate CCL display names.

The current registry cannot meet a 5–10 retailer objective generally. Source expansion and/or a narrower, deeper tracked product set is required, but no exact monitored set or source family is selected by this handover.

<decisions_made>

- Treat immutable Git artefacts as the authoritative acquisition record; do not make PostgreSQL availability a prerequisite for successful collection.
- Add an idempotent post-collection importer rather than direct collector writes to operational SQL.
- Preserve original tranche/evidence documents and source vocabulary in a raw/staging layer before normalisation.
- Persist successful and failed target attempts so every matrix blank has an auditable state.
- Keep the initial frontend static: reviewed SQL view → deterministic checksum-bound JSON export → Next.js build.
- Prefer retailer depth for a smaller exact-MPN set over broad one-retailer catalogue coverage, without selecting the actual basket or methodology yet.
</decisions_made>
